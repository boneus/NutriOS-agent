# Локальная наблюдаемость health-агента

## Назначение

Сохранять результат каждого завершившегося запуска локально, чтобы после изменения модели или промптов можно было повторить ту же задачу и прогнать небольшой стабильный набор safety/quality-проверок.

## Ограничения

- Только локальные JSON-файлы, без внешних сервисов.
- Agent loop и safety-инварианты сохраняются: максимум три раунда, одна повторная попытка при невалидном JSON reviewer-а, запись плана только после `approve`.
- Replay и eval выполняют запуски строго последовательно.
- Ошибка записи трейса не меняет результат запуска.
- Тесты, TDD и коммиты исключены по прямому требованию пользователя.

## Подходы

1. **Рекомендуемый и выбранный: запись на границе harness.** `runHealthAgent` перед возвратом передаёт готовый результат в отдельный `traceRun`. Все точки входа (UI, replay, eval) получают одинаковое поведение без дублирования.
2. Запись в API route. Проще изолировать UI, но CLI-запуски останутся без трейсов и логика разойдётся.
3. Обёртка вокруг harness. Не требует менять основной файл, но каждую новую точку входа легко ошибочно подключить напрямую.

## Дизайн

- `src/harness/traceRun.ts` преобразует полный результат в компактный trace-контракт, создаёт `runs/` и пишет `run-<timestamp>.json`. Ошибки перехватываются и только логируются.
- Reviewer получает исходную задачу вместе с планом, чтобы eval медицинского запроса действительно проверял safety gate, а не только безопасную формулировку ответа coach-а.
- `scripts/replay.ts` читает task из старого трейса, вызывает текущий harness и выводит старые/новые значения и признак изменения.
- `scripts/eval.ts` сортирует JSON-кейсы, запускает их простым циклом и выставляет ненулевой exit code при любом FAIL.
- `runs/*` игнорируется, кроме документированного `runs/run-example.json`.

## Не входит в задачу

Агрегация метрик, UI просмотра трейсов, параллельные прогоны, очереди, отдельный eval-фреймворк и персистентность неуспешных запусков, которые завершились исключением до появления verdict.
